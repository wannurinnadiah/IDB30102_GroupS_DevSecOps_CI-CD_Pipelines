## Research Overview

### Research Problem

SAST/SCA tools can produce false-positive and low-relevance security findings, which may contribute to developer alert fatigue and unnecessary CI/CD pipeline interruptions. Traditional security gates that rely mainly on fixed severity thresholds may also overlook contextual factors when deciding whether a security finding should block a pipeline.

### Research Aim

To design and develop a context-aware adaptive security gate that prioritises CI/CD security alerts based on contextual risk while minimising false-positive alert fatigue and additional pipeline execution overhead.

### Research Objectives

1. To identify contextual risk factors that affect security alert prioritisation in DevSecOps CI/CD pipelines.

2. To design and develop a prototype context-aware adaptive security gate integrated with an open-source SAST/SCA tool.

3. To evaluate the proposed security gate against a conventional non-adaptive gate based on false-positive reduction, detection accuracy, and pipeline execution overhead.

---

## Proposed Solution

The proposed solution is a context-aware adaptive security gate that supplements an existing open-source SAST/SCA tool within a CI/CD pipeline.

The framework considers five contextual factors:

- Code-change criticality
- File-path context
- Deployment environment
- Historical rule reliability
- Security finding severity

These factors are used to calculate a contextual risk score for each security finding. Based on the resulting risk level, findings are classified into three categories:

| Risk Level | Proposed Action |
|---|---|
| **Low Risk** | Suppress the finding and allow the pipeline to continue |
| **Advisory** | Report the finding with a warning without blocking the pipeline |
| **High Risk** | Block the pipeline and raise an alert |

The proposed approach aims to reduce unnecessary security alerts while maintaining effective security detection without introducing substantial additional CI/CD pipeline overhead.

## Research Methodology

### Research Methodology

**Experimental Research**

The experimental methodology will be used to compare the proposed context-aware adaptive security gate with a conventional severity-based security gate under controlled conditions.

The comparison will use the same benchmark applications and test conditions to measure false-positive reduction, detection accuracy, and CI/CD pipeline execution overhead.

### Development Model

**Iterative Prototyping Model**

The Iterative Prototyping Model will be used because the project involves developing a prototype that can be tested and refined before the final evaluation.

The development process consists of:

1. **Requirement Analysis** – Identify the required contextual factors, scanner outputs, risk categories, and gate actions.
2. **Prototype Design** – Design the context extraction, risk-scoring, and adaptive decision components.
3. **Implementation and Integration** – Implement the prototype and integrate it with the selected open-source SAST/SCA tool and CI/CD pipeline.
4. **Testing and Refinement** – Test the prototype using benchmark applications and refine the risk-scoring and decision rules before final evaluation.

## Proposed Evaluation Plan

### Evaluation Objective

The evaluation aims to determine whether the proposed context-aware adaptive security gate can reduce unnecessary security alerts while maintaining effective security detection and avoiding substantial additional CI/CD pipeline execution overhead.

### Baseline

The proposed adaptive security gate will be compared against a **conventional non-adaptive security gate**.

The conventional gate will primarily use the severity level generated by the security scanner to determine whether a finding should block the pipeline.

The adaptive and conventional configurations will use:

- The same benchmark applications
- The same security scanner
- The same CI/CD environment
- The same test conditions

This provides a controlled comparison between the two approaches.

### Dataset and Test Environment

The prototype will be evaluated using benchmark applications containing:

- Known security vulnerabilities
- Deliberately benign configurations

The proposed test environment will use:

- **CI/CD Platform:** GitHub Actions
- **Security Scanner:** Open-source SAST/SCA tool
- **Test Applications:** Benchmark applications with known vulnerabilities and benign configurations

The exact benchmark applications and scanner configuration will be finalised during implementation.

### Evaluation Metrics

The adaptive and conventional security gates will be compared using three main metrics.

#### 1. False-Positive Reduction

Measures how effectively the proposed security gate reduces unnecessary or incorrectly flagged security findings compared with the conventional gate.

#### 2. Detection Accuracy

Measures the effectiveness of the security gate in identifying relevant security findings while maintaining security detection capability.

#### 3. CI/CD Pipeline Execution Overhead

Measures the additional execution time introduced by the proposed context-aware security gate compared with the conventional security gate.

### Expected Comparison

| Evaluation Aspect | Conventional Gate | Adaptive Security Gate |
|---|---|---|
| Risk assessment | Mainly scanner severity | Severity + contextual factors |
| False-positive handling | Fixed severity-based rules | Context-aware prioritisation |
| Low-risk findings | May still trigger the gate | May be suppressed |
| Advisory findings | Severity dependent | Reported without blocking |
| High-risk findings | Block based on threshold | Block based on contextual risk |
| Pipeline overhead | Baseline | Compared against baseline |
| Detection effectiveness | Baseline | Compared against baseline |

## Proposed System Architecture

The proposed system consists of five major components:

### 1. CI/CD Pipeline

Triggers the security scanning process when a code commit is pushed to the repository.

### 2. SAST/SCA Scanner

Scans the source code and generates security findings.

### 3. Context Extraction Module

Collects relevant contextual information for each security finding, including code-change criticality, file-path context, deployment environment, historical rule reliability, and finding severity.

### 4. Risk Scoring Module

Uses the identified contextual factors to calculate a contextual risk score for each security finding.

### 5. Adaptive Decision Module

Classifies each security finding as low-risk, advisory, or high-risk and applies the corresponding pipeline action.
